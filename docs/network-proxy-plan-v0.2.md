# v0.2 网络与出口代理执行规划

日期：2026-10-22，Asia/Shanghai。状态：用户已恢复编码，NET-01/02 的合同和应用 HTTP 原型已部分实施；阶段证据见 [实施记录](./network-proxy-progress-v0.2.md)。

本文细化原方案 R06 的连接、账号与网络设置，不改变多 Agent 派工、并行范围、审查返工和用户澄清规则。设计要求与实施状态分开记录，不能把本文全体能力当作已经实现。

## 1. 这次明确的使用方式

| 连接场景 | 默认网络方式 | 预期行为 |
| --- | --- | --- |
| GPT 登录或普通 API | 跟随本机网络 | 使用当前操作系统路由；本机 TUN/VPN 和分流规则决定最终出口 |
| 国产 API / Coding Plan | 跟随本机网络 | 填写接口地址、协议、Key和模型；需要时另选代理 |
| 公司中转 | 跟随本机网络 | 配置公司 Base URL、认证与 Messages 等实际协议，验证公司 DNS/Clash 路径 |
| Claude 订阅账号 | 指定出口代理，启用严格出口约束 | 用户指定住宅代理等出口；登录、续期与推理共用该配置，故障阻断 |

规则按用户选择的连接/认证类型和账号策略确定，不根据模型名字或 Messages 协议猜测。公司接口使用 Messages，不等于它是 Claude 订阅账号。

用户网络截图显示系统代理、虚拟网卡/TUN 均开启，使用规则模式。后续因公司限制改用 Podman，本机容器环境已安装并通过基础写边界探针；产品仍保留 Docker Desktop 支持。未记录截图中的公网或内网 IP，未读取和修改 Clash 配置。

“跟随本机网络”表示平台不额外指定出口代理，不承诺裸机公网直连，也不承诺每个域名必经 VPN。TUN 关闭或规则变化后，它仍按本机网络实际状态工作。

## 2. 界面：两个互斥选项

配置放在“大模型连接/账号配置”中的“网络连接方式”。建议使用单选或分段选择，避免两个独立开关都开、都关而含义不明。

~~~text
网络连接方式
  ● 跟随本机网络（默认）
    使用当前本机网络、VPN/TUN及分流规则。

  ○ 使用指定出口代理
    代理： [选择已保存代理 ▾]  [新增代理]
    状态： 未检测 / 可连接 / 不可用
    最近检测出口：未检测
    [测试代理]
~~~

若产品视觉上使用开关，则只设一个“使用指定出口代理”：关闭对应跟随本机网络，开启对应指定代理。内部仍保存单一模式值，不能保存两个互相矛盾的布尔值。

普通连接默认选本机网络。Claude 订阅连接按前面确认的隐私目标默认选指定代理，并显示“此账号要求专用出口”；代理或严格隔离未就绪时不允许开始该账号登录，不因未配置而自动使用本机网络。

“最近检测出口”附带检测时间和对应策略版本，只证明该次检测请求。界面不能把它写成“所有请求均已保证此出口”。

## 3. 新增代理表单

| 字段 | 规则 |
| --- | --- |
| 名称 | 用户易于识别，例如“Claude 住宅出口”“本机 Clash” |
| 协议 | HTTP、HTTPS、SOCKS5；SOCKS5 的目标域名使用代理侧解析语义 |
| 地址和端口 | 分开填写，也支持粘贴完整代理 URL 后拆分 |
| 用户名、密码 | 按代理服务要求填写；保存后仅显示已配置状态 |
| 启用状态 | 停用后被引用的连接不可用，不能默认回到本机网络 |
| 检测状态 | 格式有效、代理可连接、出口检测分别记录 |

首次不支持含义含糊的无协议字符串；完整 URL 和表单字段冲突时提示修正，不能猜测密码或重复拼接协议。

密码、代理认证信息保存在本机凭证存储，普通配置仅保存引用。列表、错误、导出和日志不返回完整含密码 URL。编辑时空白密码表示保持原值，清除需要明确操作，不能因未回显密码而覆盖丢失。

代理端点固定不代表住宅公网出口一定固定，后者取决于代理服务的固定/粘性会话能力。页面如实显示实际检测结果，不自动判断或保证住宅 IP 品质。

单独一个公网 IP 不等于可连接的代理服务。实际配置需要供应商提供的代理协议、主机、端口及必要认证；“住宅 IP”描述最终出口属性。

## 4. Base URL 与出口代理分别配置

~~~text
模型服务
  接口协议：Messages
  Base URL：公司提供的服务地址
  认证：API Key / Bearer 等服务要求
  模型：公司允许使用的模型编号

网络连接
  跟随本机网络
  或 指定某个代理出口
~~~

Base URL 是请求目的地；代理地址是到达目的地的路径。二者不能共用一个输入框、互相覆盖，也不能把住宅代理地址当模型服务地址。

公司服务默认由宿主机上的模型网络服务发起 API 请求，优先沿用本机网络与解析环境。需要明确使用 Clash 本地代理时，在代理列表新增“本机 Clash”，再绑定到该连接。

不自动读取整份 Clash 配置、修改系统 DNS、替换 VPN 或向局域网开放本机代理端口。容器需要访问本机服务时由受控网关适配，不能把容器的 localhost 当作宿主机。

宿主请求也需要实测公司域名能否正确解析和到达；本机 TUN 开启不是公司 DNS 一定可用的证据。若显式选择外部住宅代理，目标 DNS 通常由该代理处理，不能再假定它知道公司内部域名。

## 5. 绑定层级与跨 Agent 一致性

界面在“大模型配置”展示，但实际绑定遵循：

~~~text
角色 → 模型连接 → 账号/凭证资源 → 网络绑定 → 指定代理或本机路由
~~~

- 同一登录账号的多个模型和角色共用账号网络绑定，避免一个模型走住宅出口、另一个模型意外改走本机。
- 同一账号被配置成多个连接别名时仍归并到相同账号资源，不能通过别名绕过网络和并发约束。
- API Key 连接可以分别配置网络；已识别为同一受保护账号资源时，冲突绑定应被拒绝或显式协调，不能随角色随机选择。
- Agent 无权自行修改代理、选择新的出口或把失败模式改成直连。
- 工作台不改变其他应用的全局出口；每个模型连接采用自己的网络策略快照。

## 6. 代理故障与配置变更

指定代理模式下，代理缺失、停用、认证失败、连不上或内部网关不可用，都返回明确的代理错误。禁止静默回落到本机、全局代理、其他代理或旧缓存连接。

与初版的“备用模型/连接”策略配合时，只有用户已预授权且符合原网络约束的备用连接才能使用。不能为了完成任务绕过 Claude 账号的专用出口要求。

不继承任意环境 NO_PROXY 作为指定代理的直连例外。内部通信和官方本地回调只允许精确、最小的通路；供应商的公网授权、续期和模型域名不能被此例外放行。

配置变更采用策略修订号：

1. 用户保存目标策略，平台说明受影响的连接和执行实例。
2. 暂停对应连接的新请求，在安全点停止受影响进程及旧链路，不暂停其他独立连接。
3. 关闭旧连接池，作废该策略的出口检测及隔离验证状态。
4. 以新策略重建执行和认证上下文，按要求检测后恢复。

用户的保存动作即对应配置变更授权，不额外给普通派工添加人工审批节点。供应商账号是否需要重新登录由实际认证状态决定，不能仅因换代理就清空全部凭证。

仍被引用的代理不允许直接删除；用户先改绑或停用。停用会使引用连接明确不可用，不能通过删除关联回到默认网络。

## 7. Claude 登录的完整链路

严格保护必须先准备网络，再开始登录：

~~~text
配置专用代理
  → 准备并验证受控网络环境
  → 在同一网络策略下打开登录浏览器
  → 官方授权与回调
  → 换取/续期凭证
  → 模型请求与必要服务请求
~~~

登录浏览器、官方执行器和服务端认证请求都需要覆盖。不能在普通浏览器直接完成登录后，只给推理请求设置代理，就声明整个登录过程使用了住宅出口。

受控网络环境的普通应用流量只允许连接指定代理，其他外联被网络规则阻断；目标域名经代理处理，IPv6、DNS、UDP/QUIC 和浏览器旁路均纳入测试。内部平台通道与回调有最小例外，不承担公网直连功能。

代理断开时强制失败。验证过的镜像、网关、代理绑定或策略版本改变时，严格就绪状态失效，需要重新验证。环境变量只是适配的一部分，不能代替网络层约束。

官方允许的认证接入方式仍须遵守原 M0 核验要求；参考项目的 OAuth 实现不是可直接复制和宣称正式支持的证据。

当前 Podman 基础写边界已验证，但严格执行环境、专用代理和登录浏览器的组合仍未实现/验收。运行时可用不能代替网络隔离验证，也不能把严格模式降级成普通代理后标为通过。

## 8. UI 两选项与内部实现的映射

| 用户选择 | 连接策略 | 内部已有原型对应值 | 可宣称的能力 |
| --- | --- | --- | --- |
| 跟随本机网络 | 系统路由和系统解析 | system | 不额外指定代理；不替用户保证 VPN |
| 指定代理，普通 API 连接 | 明确的应用请求代理 | explicit_proxy | 工作台该请求路径失败不回退 |
| 指定代理，受保护 Claude 订阅 | 账号完整链路和网络层隔离 | enforced_proxy | 真实隔离与认证测试通过后才可标为严格就绪 |

后端的第三种能力不是第三个普通用户选项，由账号保护要求派生。前端不能提交一个 protection=false 就解除受保护账号的要求。

若以后只开启系统 HTTP 代理而关闭 TUN，需要显式绑定“本机 Clash”或实现经验证的系统代理适配；不能假定所有 Go/CLI 客户端自动读取 macOS UI 代理设置。

## 9. 建议数据与接口合同

本节描述目标字段。代理元数据和账号二选一绑定的 v1 Schema 已加入 M0；其余字段、持久服务与界面按阶段继续实施。

ProxyEndpoint 保存代理 ID、名称、类型、地址、端口、凭证引用、启用状态和修订号。检测记录独立保存结果、时间、策略修订和证据类型。

NetworkBinding 保存 owner_type（connection/account）、owner_id、ui_mode（system/proxy）、proxy_id 和 policy_revision。账号保护要求由受信任的账号策略决定；不能由模型或浏览器字段自报解除。

AuthContext 绑定账号资源、认证实例和网络策略修订。登录链接、授权事务、续期执行者和模型执行器使用同一绑定快照；过期的认证事务不能悄悄采用新的默认出口。

拟增加的接口职责：代理增改查、代理停用、代理检测、连接/账号网络绑定、当前就绪状态。所有写入由用户配置身份授权；Agent 工具只读取脱敏的有效策略与不可用原因。

## 10. codex-proxy 的参考价值

本次阅读其 dev 分支的说明和相关源码，未安装或启动该项目。它提供按账号分配代理、代理表单和出口健康信息，可借鉴为配置体验。[项目说明](https://github.com/icebear0828/codex-proxy#-代理池)

需要明确调整的语义：其代理解析函数在部分缺失/停用情形返回表示全局配置的 undefined；我们的“指定代理”应返回明确错误。[代理分配源码](https://github.com/icebear0828/codex-proxy/blob/dev/src/proxy/proxy-pool.ts)

其 dispatcher 支持全局代理与 NO_PROXY；我们的严格账号必须使用显式、受控的例外范围。[请求路由源码](https://github.com/icebear0828/codex-proxy/blob/dev/src/proxy/fetch-dispatcher.ts)

其代理管理接口支持完整 URL 或拆分字段，可以参考输入方式。[代理接口源码](https://github.com/icebear0828/codex-proxy/blob/dev/src/routes/proxies.ts)

本次仅参考这些机制，不引入自动账号轮换、自动换 IP、指纹模拟或额外协议转换功能。用户无需为配置工作台网络而先学会部署该项目。正式复用源码前固定提交并核对许可。

## 11. 可执行的实施顺序

以下任务已按用户恢复编码的指令推进。原 M0–M6 阶段门禁继续有效；逐项已完成/待验证状态见实施记录。

| 任务 | 所属阶段/前置 | 开发范围 | 完成条件 |
| --- | --- | --- | --- |
| NET-01 固定交互和规则 | 本规划确认后 | 网络合同、文案与设计说明 | 两选项互斥、默认值、账号保护及故障语义确定 |
| NET-02 M0 路径与隔离原型 | NET-01；严格分支需 Docker/Podman 运行时与网络隔离验证 | 网络策略、代理适配、隔离探针 | 本机/显式代理/严格保护分别有证据，未验证状态不能混淆 |

| NET-04 配置界面 | NET-03；原 M1/M2 Web基础 | 模型连接表单、代理表单、状态展示 | 用户能完成本机、住宅代理、公司中转三种配置 |

| NET-06 多连接与故障验收 | NET-04/05 | 端到端与实际网络验证 | 并行连接互不污染；断网、切换、重启与旧策略均按合同处理 |

普通 API 配置可以先用合成服务验证；严格分支必须通过真实网络实验。不能用 NET-04 的界面完成代替 NET-02/05 的网络能力完成，也不能绕过原 M0 条件直接宣布进入正式交付。
